### ラウンド1（2026-08-18）

#### Q1: 旧 `knowledge-vault-generation` の要件ID体系をどう扱うか

**カテゴリ**: 既存設計確認
**背景**: 発見1。MediaVault 側の設計判断（D-07〜D-10、失敗クラス対応表）がこれらのREQ番号を根拠にしている。番号を振り直すと相手側の設計根拠が宙に浮く。

**回答**: **継承する**

**信頼性への影響**: 出力先を `docs/spec/knowledge-vault-generation/` に確定。REQ-006 / REQ-016a / REQ-101 / REQ-105 / REQ-202 / REQ-401 / REQ-402 / NFR-031 / NFR-101 / EDGE-006 の10項目が、MediaVault 側文書という一次資料の裏付けを得て 🔵 で確定した。

- NFR-101 を「MVP は単一トークン運用」から「readonly トークン運用・スコープ拡張が前提」へ更新（🔵）。旧 PRD §15 の「Mastra側のツール選別を必須の防御線とする」方針は、REQ-401 と併存する二重防御として維持。
- prep.md の**必須**タスク1件を新規追加。

## ヒアリング結果サマリー

### 確認できた事項

- 要件ID体系は旧 `knowledge-vault-generation` を継承する（出力先ディレクトリ名も同じ）
- MediaVault MCP は readonly トークンで接続する。`get_item_text` のスコープ追加が前提条件
- Vault 操作は Mastra 内部 Tool として実装する
- 今回の要件定義は PRD §5 MVP の6項目に限定する
- LLM は役割別の論理モデル名で切り替える
- 未抽出ファイルは通知のみ。Mastra から抽出を依頼しない
- 章境界が推定になった場合は生成したうえで `review_needed`
- MVP の起動は Mastra Studio 手動のみ
- 性能目標は「専門書1冊が一晩（8時間）以内」
- 確認待ちは用途別に `00 Inbox` / `90 Meta` / `ai-workspace` へ振り分ける

### 追加/変更要件

| 種別 | 内容 |
|---|---|
| **変更** | NFR-101: 単一トークン運用 → readonly トークン運用（スコープ拡張が前提） |
| **変更** | REQ-411 の新設により、PRD §7「書き込み前一致確認」を撤回。競合回復は git 履歴に一本化 |
| **追加** | REQ-412: Vault 操作は内部 Tool として実装（独立 MCP サーバーにしない） |
| **追加** | REQ-410: MVP の起動は Mastra Studio 手動のみ |
| **追加** | NFR-001: 専門書1冊 8時間以内 |
| **確定** | PRD §8 の未確定事項9件のうち **6件を解決**（論理モデル名の名前空間 / `get_item_text` の可否 / Vault MCP 形態 / 未抽出対応 / 章分割の閾値 / 起動方式）。加えて「確認待ちキューの置き場」「生成コストの許容範囲」も解決 |

### 残課題

- **PRD §8「話数とMediaVault上のファイルの対応づけ」** — フェーズ2（`generateEpisodeKnowledgeWorkflow`）の課題のため本要件では扱わない
- **PRD §8「Web検索の経路」** — フェーズ2（`researchTopicWorkflow`）の課題
- **PRD §8「動画・音声の文字起こし」** — 実際に1作品試してから判断する方針のまま
- **論理モデル名の具体的な命名リスト** — 「役割別に新設」まで決定。個々の名前と実体割り当ては LiteLLM config を見て確定する必要がある（prep.md 必須タスク）
- **`get_item_text` の readonly スコープ追加** — MediaVault 側の実装が完了するまで MVP 中核は動かない（prep.md 必須タスク・最大のブロッカー）
- **テストランナー未導入** — `npm test` が未設定のため、acceptance-criteria.md のテストケースを自動化するには別途セットアップが必要
- **MediaVault 側文書のリンク切れ** — `intrahub-mastra PRD §15` への参照が現行 PRD と合わない。修正は `intrahub-mediavault` の管轄
