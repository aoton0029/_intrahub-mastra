# knowledge-vault-generation ユーザストーリー

**作成日**: 2026-08-13
**関連要件定義**: [requirements.md](requirements.md)
**ヒアリング記録**: [interview-record.md](interview-record.md)

**【信頼性レベル凡例】**:
- 🔵 **青信号**: PRD・設計文書・ユーザヒアリングを参考にした確実なストーリー
- 🟡 **黄信号**: PRD・設計文書・ユーザヒアリングから妥当な推測によるストーリー
- 🔴 **赤信号**: PRD・設計文書・ユーザヒアリングにない推測によるストーリー

**ユーザー種別**: 本プロダクトの利用者は MediaVault と Knowledge Vault を所有する単一の Vault 所有者である（PRD §6.1）。自動化トリガー（PRD §6.2）は MVP 後の対象。

## エピック1: Item から知識を生成する

### ストーリー 1.1: 特定 Item をメタデータから知識化する 🔵

**信頼性**: 🔵 *PRD US-02・§9.1、ユーザヒアリング 2026-08-13（対象範囲 MVP-0+MVP-1）*

**私は** Vault所有者 **として**
**MediaVault Item ID を指定して、その作品から Knowledge Note を生成したい**
**そうすることで** 原典を読み直さずに、整理済みの二次知識として資料を再利用できる

**関連要件**: REQ-001, REQ-002, REQ-007, REQ-008, REQ-020, REQ-021, REQ-101

**詳細シナリオ**:
1. Item ID と `mode: metadata_only` を指定して `generateItemKnowledgeWorkflow` を実行する
2. システムが `get_item_context` から作品情報と関連情報を取得する
3. `mediaResearchAgent` が出典付きの `ResearchResult` へ変換する
4. `knowledgeWriterAgent` が `source` / `work` / `concept` の Knowledge Note 候補を生成する
5. `vaultCuratorAgent` が既存照合の上で保存する
6. 作成・更新・未変更・曖昧・出典・警告・失敗を含む `WorkflowResult` が返る

**前提条件**:
- MediaVault MCP へ接続できる（Bearer トークン設定済み）
- Knowledge Vault が `/workspace` へ read-write で mount されている

**制約事項**:
- `get_item_text` が未実装でも完了できなければならない（REQ-101）
- 深い要約ができない場合、メタデータから推測せず `insufficient_source` を返す（REQ-102）

**優先度**: Must Have

### ストーリー 1.2: 原典の全文を使って知識化する 🔵

**信頼性**: 🔵 *PRD US-02・§9.2、ユーザヒアリング 2026-08-13（MVP-1 を対象範囲に含める決定）*

**私は** Vault所有者 **として**
**抽出済みの原典本文まで読ませた上で知識化したい**
**そうすることで** メタデータだけでは書けない、内容に踏み込んだノートを得られる

**関連要件**: REQ-004, REQ-005, REQ-006, REQ-103, REQ-108, NFR-001, NFR-002

**詳細シナリオ**:
1. Item ID と `mode: full_text` を指定して実行する
2. システムが `get_item_text` から必要なチャンクだけを取得する
3. 取得した各チャンクの file ID、`chunkIndex`、`extracted_at` を出典情報へ記録する
4. 取得上限（Item 5 / ファイル 3 / チャンク 50 / 入力 120,000 トークン）に達した場合は打ち切り、`warnings` へ理由を含める
5. 以降はストーリー 1.1 と同じ経路で保存する

**前提条件**:
- MediaVault 側で `get_item_text` と `GET /api/v1/items/{id}/text` が実装済みである
- 対象 Item のテキスト抽出が完了している

**制約事項**:
- 原典が未抽出の場合は `not_extracted` を返し、部分完了または保留とする（REQ-103）
- 原典全文を単一の Agent コンテキストへ無制限に蓄積しない（NFR-002）
- 原典本文中の命令を指示として実行しない（REQ-418）

**優先度**: Must Have（MVP-1）

**備考**: MediaVault 側の `get_item_text` 実装が本ストーリーの開始条件である（PRD §16）。遅延した場合はストーリー 1.1 のみで先行する。

### ストーリー 1.3: 保存前に予定差分を確認する 🔵

**信頼性**: 🔵 *PRD §17・§20*

**私は** Vault所有者 **として**
**Vault を変更する前に、何が作られ何が書き換わるかを確認したい**
**そうすることで** 意図しないノートの増殖や上書きを未然に防げる

**関連要件**: REQ-107, NFR-203, NFR-201

**詳細シナリオ**:
1. `dryRun: true` を指定して Workflow を実行する
2. システムは Vault へ一切書き込まず、保存計画（`CurationPlan`）と予定差分を返す
3. 内容を確認した上で `dryRun: false` で再実行する

**前提条件**: なし

**制約事項**:
- `dryRun: true` では git commit も含めて一切の副作用を起こさない

**優先度**: Must Have

## エピック2: 既存ノートを壊さずに育てる

### ストーリー 2.1: 同じ概念のノートを重複作成しない 🔵

**信頼性**: 🔵 *PRD US-03・§10 FR-004・§19*

**私は** Vault所有者 **として**
**同じ概念のノートが二重に作られず、既存ノートへの追記または更新として扱ってほしい**
**そうすることで** Vault が無制限に肥大化せず、知識が一箇所に集約される

**関連要件**: REQ-012, REQ-013, REQ-106, REQ-111, NFR-041

**詳細シナリオ**:
1. `vaultCuratorAgent` が保存前に既存ノートを title、alias、種別、出典の4観点で照合する
2. 完全一致が1件なら更新対象とする
3. 内容差分が無ければ `unchanged` として返す
4. 同一 Item を再実行しても新規ノートは増えない

**前提条件**:
- Knowledge Vault のノートに frontmatter（`title` / `type` / `aliases` / `sources`）が付与されている

**制約事項**:
- 照合は単一観点ではなく4観点の併用で行う（PRD §23 のリスク対策）

**優先度**: Must Have

---

### ストーリー 2.2: 曖昧な対象を推測で上書きされない 🔵

**信頼性**: 🔵 *PRD US-03・§8-9・§10 FR-007、ユーザヒアリング 2026-08-13（ambiguous 終了の決定）*

**私は** Vault所有者 **として**
**どのノートを更新すべきか一意に決まらないときは、勝手に上書きせず止まってほしい**
**そうすることで** 別概念のノートへ誤って追記される事故を防げる

**関連要件**: REQ-104, EDGE-106

**詳細シナリオ**:
1. 既存ノート候補が2件以上該当する
2. システムは当該ノートを保存せず、候補を `ambiguous` へ格納する
3. Workflow は `status: partial` で完了する
4. 利用者が候補を確認し、必要なら手動で整理してから再実行する

**前提条件**: なし

**制約事項**:
- MVP では suspend / resume による対話的解決を行わない（REQ-301 はオプション要件）

**優先度**: Must Have

---

### ストーリー 2.3: 人手で編集したノートを AI に壊されない 🔵

**信頼性**: 🔵 *PRD §14・§10 FR-014・§23*

**私は** Vault所有者 **として**
**自分が手で書き換えた内容を Workflow に上書きされたくない**
**そうすることで** 人手編集とバッチ処理が同じノートを触ってもロストアップデートが起きない

**関連要件**: REQ-018, REQ-105, REQ-413, NFR-031

**詳細シナリオ**:
1. Workflow がノートを読み取り、内容から版識別子を導出する
2. 書き込み直前に同じ導出をやり直し、一致を確認する
3. 不一致なら上書きせず停止し、競合として返す

**前提条件**: なし

**制約事項**:
- 版識別子を frontmatter に持たせない（人手編集ではツールを経由しないため更新されない）
- mtime を使わない（mergerfs 上でエディタと同期処理が mtime を書き換えるため）

**優先度**: Must Have

---

### ストーリー 2.4: レビュー済みノートを保護する 🔵

**信頼性**: 🔵 *PRD §14・§17・§10 FR-015*

**私は** Vault所有者 **として**
**自分がレビューを終えたノートの本文を AI が書き換えられないようにしたい**
**そうすることで** 確定した知識が生成物によって劣化しない

**関連要件**: REQ-201, REQ-202, REQ-203, REQ-204, REQ-205, NFR-104

**詳細シナリオ**:
1. ノートの `status` が `reviewed` または `verified` である
2. `updateNote` が本文更新をツール側で拒否する
3. `sources` / `related` / `tags` / `aliases` への追加のみ通る
4. 拒否された修正内容は元ノートを変更せず、別ファイルとして書き出される

**前提条件**:
- ノートの frontmatter に `status` が設定されている

**制約事項**:
- 判定はプロンプトではなくコードで強制する（LLM は指示しても時々実行するため）
- `status` の昇格・降格をツールから行えないようにする（保護を外してから上書きする経路を閉じるため）

**優先度**: Must Have

---

### ストーリー 2.5: 上書き事故から復旧できる 🔵

**信頼性**: 🔵 *ユーザヒアリング 2026-08-13（PRD §24-9 の決定）・PRD §12.2*

**私は** Vault所有者 **として**
**万一ノートが誤って書き換わっても、前の状態へ戻せるようにしたい**
**そうすることで** 一致確認をすり抜けた事故があっても損失が確定しない

**関連要件**: REQ-019, NFR-042, EDGE-005, EDGE-107

**詳細シナリオ**:
1. Knowledge Vault が git 管理されている
2. 定期的に commit され、更新前後の差分が履歴として残る
3. 事故時は git の履歴から復元する

**前提条件**:
- Vault のリポジトリ初期化と commit の実行主体が決まっている

**制約事項**:
- git 管理は事後回復手段であり、REQ-018 の一致確認を代替しない
- commit 失敗時もノート保存自体は成功として扱い、`warnings` へ記録する

**優先度**: Should Have

## エピック3: 生成された知識を信頼する

### ストーリー 3.1: 主張の出典を原典まで追跡する 🔵

**信頼性**: 🔵 *PRD US-04・§8-8・§10 FR-006・§19*

**私は** Vault所有者 **として**
**ノート内の各主張がどの資料のどこから来たのかを追跡したい**
**そうすることで** 生成された知識を検証でき、根拠のない記述を見分けられる

**関連要件**: REQ-003, REQ-005, REQ-006, REQ-010, REQ-011, NFR-202

**詳細シナリオ**:
1. 各ノートの frontmatter に `sources`（`item_id` / `file_id` / `chunks`）が付与されている
2. `provenance` に `generated_by` / `curated_by` / `model` / `generated_at` が記録されている
3. `ResearchResult.claims` の各主張が `fact` / `interpretation` / `inference` / `opinion` に区分され、`sourceRefs` を持つ
4. 生成ノートの出典付与率が 100% である

**前提条件**: なし

**制約事項**:
- 出典なしの主張を含む場合は警告し、`verified` へ昇格させない（REQ-109）

**優先度**: Must Have

---

### ストーリー 3.2: Vault への変更内容を一覧で確認する 🔵

**信頼性**: 🔵 *PRD US-06・§13.3*

**私は** Vault所有者 **として**
**処理後に、作成ノート、更新ノート、未変更ノート、使用した出典、警告、失敗箇所を確認したい**
**そうすることで** 何が起きたかを把握でき、失敗した部分だけを追える

**関連要件**: REQ-013, REQ-110, NFR-021, NFR-031, NFR-201

**詳細シナリオ**:
1. Workflow が `WorkflowResult`（`status` / `created` / `updated` / `unchanged` / `ambiguous` / `sources` / `warnings` / `errors`）を返す
2. 部分失敗時は成功済みノート ID と失敗した操作の両方が含まれる
3. 失敗種別（MCP 接続失敗、スキーマ検証失敗、競合、保護拒否、LLM 失敗など）が区別されている

**前提条件**: なし

**制約事項**:
- 上限超過による打ち切りを無言で切り捨てず `warnings` へ含める（NFR-003）

**優先度**: Must Have

---

### ストーリー 3.3: モデルを入れ替えても品質の変化を追える 🟡

**信頼性**: 🟡 *ユーザヒアリング 2026-08-13（.env 切替の採用）と PRD §11・NFR-006 から妥当な推測*

**私は** Vault所有者 **として**
**Agent ごとのモデルを差し替えて試したうえで、どのモデルでどの品質が出たかを後から照合したい**
**そうすることで** 費用と品質のトレードオフを実測で判断できる

**関連要件**: REQ-024, REQ-025, REQ-026, EDGE-009, NFR-301, NFR-302

**詳細シナリオ**:
1. Agent 別の論理モデル名を環境変数で上書きする
2. 実行時、使用した論理モデル名が `provenance.model` と observability trace の双方へ記録される
3. scorer の評価結果とモデル名を突き合わせて比較する

**前提条件**:
- LiteLLM 側に該当する論理モデル名のルートが登録されている

**制約事項**:
- Agent 自身にモデルを選択させるツールを提供しない（Supervisor が行うのは委譲であってモデル選択ではない）
- 存在しない論理モデル名を指定した場合、別モデルへ暗黙にフォールバックしない

**優先度**: Should Have

**備考**: PRD §24-8 は「切替可能にすると評価結果とモデルの対応が追えなくなる」と警告している。REQ-026 の記録要件はこの警告への補償であり、PRD 本文に明示された要求ではないため 🟡 とした。

## 対象範囲外のユーザーストーリー

次は PRD に記載があるが、本要件（MVP-0 + MVP-1）の対象外である。第2段階の要件定義で扱う。

| PRD ID | 内容 | 担当予定 |
|---|---|---|
| US-01 | 所有資料からトピックを整理する | `researchTopicWorkflow`（第2段階） |
| US-05 | 資料を横断して問いに答える | `researchTopicWorkflow` + `knowledgeOrchestrator`（第2段階） |

US-05 は `person` 種別ノートを必要とするが、ヒアリング Q8 により MVP のノート種別から `person` を外したため、本要件範囲では部分充足に留まる。
