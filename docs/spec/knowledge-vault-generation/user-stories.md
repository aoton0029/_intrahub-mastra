## エピック1: OCR済み文献の章要約（MVP の中核）

### ストーリー 1.1: 論文・専門書を章ごとに要約して Vault へ残す 🔵

**信頼性**: 🔵 *PRD §4 ユーザーストーリー1・§5「summarizeDocumentWorkflow」より*

**私は** コレクション所有者 **として**
**OCR した論文・専門書を章ごとに要約して Vault へ保存したい**
**そうすることで** 全文は量が多くて読み返せないが、章単位の要約なら参照でき、死蔵状態を解消できる

**関連要件**: REQ-005, REQ-007, REQ-014, REQ-017, REQ-301, NFR-002

**詳細シナリオ**:
1. Mastra Studio（`:4111`）で `summarizeDocumentWorkflow` を開き、対象資料を指定して起動する
2. Workflow が `search_library` で Item を解決し、`get_item_context` でファイル一覧と書誌情報を取得する
3. `get_item_text` で抽出済みテキストを0起点連番のチャンクとして取得する
4. チャンク → 章 → 文献全体の順に階層要約する。全文を一度に LLM へ渡さない
5. `10 Sources/Academic Books/{著者}-{年}-{短縮タイトル}/` に `index.md` と `Chapters/` 配下の章ノートを `status: draft` で生成する
6. Obsidian で `index.md` を開き、章一覧から目的の章へ辿る

**前提条件**:
- 対象ファイルが MediaVault Extractor で抽出済みである
- mediavault-mcp が起動し、readonly トークンで `get_item_text` が見えている

**制約事項**:
- OCR 全文を Vault へ複製しない（REQ-404）
- 専門書1冊が一晩（8時間）以内に完了する（NFR-001）

**優先度**: Must Have

### ストーリー 1.2: 各記述の根拠を原典まで辿る 🔵

**信頼性**: 🔵 *PRD §3 成功指標「`(itemId, fileId, chunkIndex)` まで遡れる」より*

**私は** コレクション所有者 **として**
**章ノートの主要な主張から、どの Item・どのファイル・どのチャンクに基づくのかを辿りたい**
**そうすることで** 生成された要約を鵜呑みにせず、疑わしい記述を原典で確認できる

**関連要件**: REQ-003, REQ-006, REQ-011, REQ-012, REQ-014

**詳細シナリオ**:
1. 章ノートの frontmatter で `sources`（`item_id` / `file_id` / `extraction_version`）を確認する
2. `source_refs`（`source` / `chunk_index` / `label`）から該当チャンクを特定する
3. 必要なら MediaVault 側で当該チャンクの原文を参照する
4. `provenance` からどの Workflow・どの実行・どのモデルが生成したかを確認する

**前提条件**:
- 出典が `(itemId, fileId, chunkIndex)` の連番形式で統一されている（REQ-006）

**優先度**: Must Have

### ストーリー 1.3: 章境界が怪しい資料を見分ける 🔵

**信頼性**: 🔵 *ヒアリング2026-08-18 Q7・PRD §5 より*

**私は** コレクション所有者 **として**
**章境界を OCR 本文から推定した資料を、確定できた資料と区別したい**
**そうすることで** 章の切り方が間違っているかもしれないノートだけを重点的に見直せる

**関連要件**: REQ-103, REQ-106, EDGE-102

**詳細シナリオ**:
1. Workflow が `chunk.label` を確認する
2. `label` が `null` で章境界を確定できない場合、見出しパターン等から推定して章ノートを生成する
3. 当該ノートの `status` を `review_needed` にする
4. Obsidian で `status: review_needed` を検索し、推定で作られたノートを一覧する

**前提条件**:
- `status` の5値がノート規約として確定している（REQ-004）

**制約事項**:
- 推定を理由にノート生成自体を止めない（生成したうえでフラグを立てる）

**優先度**: Must Have

## エピック2: Vault の規約と操作

### ストーリー 2.1: Obsidian でそのまま読める構成で蓄積される 🔵

**信頼性**: 🔵 *PRD §5・§7・codex-chat.md「Knowledge Vaultの構成」より*

**私は** コレクション所有者 **として**
**生成物が `00 Inbox` 〜 `90 Meta` の決まった大分類に、決まった frontmatter で置かれてほしい**
**そうすることで** Obsidian と Samba から普段どおり読み書きでき、ノートが増えても構造が崩れない

**関連要件**: REQ-001, REQ-002, REQ-003, REQ-004, NFR-201, NFR-202

**詳細シナリオ**:
1. `/srv/knowledge/second-brain` が7大分類で構成されている
2. ノート種別はディレクトリではなく frontmatter の `type`（11種）で管理される
3. 全ノートが共通 frontmatter を持つ
4. ファイル所有者が `LIBRARY_UID` と人間の編集者で揃っており、Samba 経由で編集できる

**優先度**: Must Have

---

### ストーリー 2.2: ノートを意味のある単位で操作させる 🔵

**信頼性**: 🔵 *PRD §5「Vault MCPとして公開するノート操作」・ヒアリング2026-08-18 Q3 より*

**私は** コレクション所有者 **として**
**AI に渡す Vault 操作を、汎用ファイル操作ではなく `search_notes` / `read_note` / `create_note` / `update_note` / `find_related_notes` の5つに限定したい**
**そうすることで** Vault 全体に対する任意のファイル操作という危険な権限を与えずに済む

**関連要件**: REQ-008, REQ-303, REQ-412

**詳細シナリオ**:
1. 5操作が Mastra 内部の Tool として `src/mastra/tools/` に実装される
2. すべて `src/mastra/index.ts` へ登録される
3. Agent には汎用の read/write ファイルツールを渡さない

**制約事項**:
- 独立した MCP サーバーとしては立てない（REQ-412）

**優先度**: Must Have

---

### ストーリー 2.3: 中間データと正本を分ける 🔵

**信頼性**: 🔵 *PRD §1・§7・codex-chat.md「責務の境界」より*

**私は** コレクション所有者 **として**
**章分割結果・下書き・レビュー結果を `ai-workspace` に置き、`second-brain` には検証を通った成果だけを残したい**
**そうすることで** Obsidian の Vault が再生成可能な作業ゴミで汚れない

**関連要件**: REQ-015, NFR-032

**優先度**: Must Have

## エピック3: 安全な書き込み

### ストーリー 3.1: 新規は自動、更新は確認 🔵

**信頼性**: 🔵 *PRD §5「書き込みポリシー」・ヒアリング2026-08-18 Q11 より*

**私は** コレクション所有者 **として**
**新規ノートは自動で作ってよいが、既存ノートの上書き・タグ削除・taxonomy 統合は自分が承認してから確定してほしい**
**そうすることで** 全件を人手で確認する余裕はないが、誤りが正本へ混ざるのも避けられる

**関連要件**: REQ-010, REQ-105, REQ-108, REQ-201, REQ-203

**詳細シナリオ**:
1. 対象資料のノートが存在しなければ `status: draft` で自動作成する
2. 既に存在する場合は更新経路へ回す
3. 上書き・タグ削除・taxonomy 統合は自動確定させず、ノート本体は `00 Inbox`、差分・検証レポートは `90 Meta` へ送る
4. `status: human_verified` のノートは自動で本文を上書きしない
5. 人間が `00 Inbox` と `90 Meta` を見て承認する

**前提条件**:
- 確認待ちの送り先が用途別に決まっている（REQ-201）

**優先度**: Must Have

---

### ストーリー 3.2: 自分が付けたタグが黙って消えない 🔵

**信頼性**: 🔵 *PRD §3 成功指標・codex-chat.md「タグ・カテゴリの管理」より*

**私は** コレクション所有者 **として**
**手で追加したタグと手で編集した本文が、AI の再生成によって黙って消えないでほしい**
**そうすることで** 手を入れた分の労力が失われる不安なく、AI に再実行させられる

**関連要件**: REQ-202, REQ-203, REQ-204, REQ-411

**詳細シナリオ**:
1. 人間が追加したタグを既定で保護する
2. 再生成で出てこなかったことだけを理由にタグを削除しない
3. `90 Meta` の taxonomy に未登録の語は正式タグにせず提案として蓄積する
4. 万一上書きされた場合は `knowledge-vault-commit.sh` の git 履歴から回復する

**制約事項**:
- Mastra 側で書き込み前の内容一致確認は実装しない（REQ-411）。回復は git に依存する

**優先度**: Must Have

---

### ストーリー 3.3: 信頼できないものだけを分離して確認する 🔵

**信頼性**: 🔵 *PRD §4 ユーザーストーリー5・§3 成功指標より*

**私は** コレクション所有者 **として**
**生成物のうち出典不足・推定・競合を含むものだけを `review_needed` として分離してほしい**
**そうすることで** 確認対象を絞りつつ、`reviewed` と混ざらない状態を保てる

**関連要件**: REQ-004, REQ-103, REQ-104, REQ-106

**優先度**: Must Have

## エピック4: 外部システムとの境界

### ストーリー 4.1: MediaVault を壊さない 🔵

**信頼性**: 🔵 *PRD §6 スコープ外・既存REQ-401 / REQ-402 より*

**私は** コレクション所有者 **として**
**知識生成の副作用で MediaVault の Item・評価・視聴読了状況・タグ・関連が変わらないと保証してほしい**
**そうすることで** Mastra 側のツール選択ミスがあっても MediaVault の正本が汚れない

**関連要件**: REQ-401, REQ-402, REQ-403, REQ-413, REQ-414, NFR-101

**詳細シナリオ**:
1. `MCP_READONLY_TOKEN` で mediavault-mcp へ接続する
2. `tools/list` に書き込みツールが現れない
3. `mediaResearchAgent` へ渡すのは `search_library` / `get_item_context` / `get_item_text` の3ツールのみ
4. サーバー側とクライアント側の二重で書き込みを封じる

**前提条件**:
- mediavault-mcp 側で readonly トークンのスコープに `get_item_text` が追加済み（→ [prep.md](prep.md) 必須タスク）

**優先度**: Must Have

---

### ストーリー 4.2: 抽出されていない資料を検出して抽出依頼に回す 🔵

**信頼性**: 🔵 *PRD §6「未抽出のファイルは `not_extracted` として抽出依頼を促す」・ヒアリング2026-08-18 Q6 より*

**私は** コレクション所有者 **として**
**まだ OCR されていない資料を処理しようとしたら、中途半端なノートを作らずに抽出依頼待ちとして知らせてほしい**
**そうすることで** 何が足りなくて処理が進まないのかがすぐ分かる

**関連要件**: REQ-102, REQ-406, NFR-031, NFR-032, EDGE-101

**詳細シナリオ**:
1. `get_item_text` が `outcome: not_extracted` を返す
2. Workflow が Mastra から抽出を依頼せず処理を中断する
3. 抽出依頼待ちとして `ai-workspace` へ記録し、人へ通知する
4. 人間が MediaVault 側で抽出を実行してから Workflow を再実行する

**制約事項**:
- `request_extraction` を呼ばない（書き込み扱いになるため）

**優先度**: Must Have

---

### ストーリー 4.3: ツール不在と未抽出を取り違えない 🔵

**信頼性**: 🔵 *mediavault-mcp design/api-tool-mapping.md D-09・既存TC-004-E02 より*

**私は** コレクション所有者 **として**
**`get_item_text` そのものが提供されていない状況を、個別ファイルの未抽出と区別して扱ってほしい**
**そうすることで** 「サーバー側が未対応」と「この資料がまだ抽出されていない」で異なる対処ができる

**関連要件**: REQ-101, NFR-031

**詳細シナリオ**:
1. Workflow が `tools/list` に `get_item_text` があるか確認する
2. 無ければツール不在として検出し、`mode: metadata_only` へフォールバックする
3. 暗黙のフォールバックはせず、フォールバックしたことを記録する

**優先度**: Must Have

---

### ストーリー 4.4: モデルの実体を後から差し替える 🔵

**信頼性**: 🔵 *PRD §5「役割別の論理モデル名」・ヒアリング2026-08-18 Q5 より*

**私は** コレクション所有者 **として**
**要約・批評・分類といった役割ごとに論理モデル名を指定し、実体（vLLM のローカルモデル / 外部API）を LiteLLM 側で差し替えたい**
**そうすることで** コードを触らずにモデルを乗り換えられ、Mastra へ `VLLM_API_KEY` を渡さずに済む

**関連要件**: REQ-009, REQ-408, NFR-102, EDGE-002

**優先度**: Must Have

---

### ストーリー 4.5: 再抽出で出典がずれたことに気づく 🔵

**信頼性**: 🔵 *PRD §5・mediavault-mcp design/api-tool-mapping.md D-08 より*

**私は** コレクション所有者 **として**
**再抽出でチャンク境界がずれたとき、保存済みノートの出典が黙って別の箇所を指す事態を避けたい**
**そうすることで** 出典が壊れたノートを `stale` として洗い出せる

**関連要件**: REQ-011, REQ-104

**詳細シナリオ**:
1. ノートの `sources[].extraction_version` を保持しておく
2. 現在の `extraction_version` と異なることを検出する
3. 参照を自動で読み替えず `status: stale` にする
4. 再調査（フェーズ2 `refreshStaleSourcesWorkflow`）の対象とする

**優先度**: Should Have（検出は MVP、再調査 Workflow はフェーズ2）
